Ground rules for the whole semester
  • Scrum: sprints, a Scrum Master, a Product Owner
  • At least 4 stand-ups a week, one in the tutorial
  • Write minutes for meetings
  • Commit often. Never push the whole codebase at once.
  • A working app at the end of every sprint
  • MVC, loosely coupled design, coding standards
  • Refactor throughout, not just at the end
  • Everyone codes, tests, documents and integrates
  • Keep the GitHub Projects board up to date
  • Credit external code and libraries; follow their licences
Ways to lose marks
  • ✕
    Repo not made through Classroom 500 marks, even if the work is good
  • ✕
    Board not kept up to dateNo progress mark
  • ✕
    Whole codebase in one big commitMarks deducted. Commit small and often.
  • ✕
    Building something not in the SRSUpdate the SRS first, before the weekly discussion
  • ✕
    Tasks bigger than 8 hoursSplit them into 1–3 hour tasks
  • ✕
    Decisions only in chatRecord every decision in the repo's docs folder

Part 2 · Milestone 1

Requirements gathering & system design · due Fri 20 Nov 2026

Plan the whole app before writing it: requirements, architecture, and a working Scrum board. You hand in one thing, your repo URL on Canvas. Everything else lives in the repo under docs/Milestone1/.

The four things to deliver

1Repo & setup

  • Repo made through Classroom 50 in the RMIT GitHub org
  • Every member has access
  • Separate folders for docs, code, assets
  • README: team name, all members, links

2SRS document

1 Introduction5 UI design2 Functional reqs6 Assumptions & constraints3 Non-functional reqs7 Dependencies4 System architecture8 Glossary
Split sections across the team, then review together. It doesn't have to be finished yet.

3Architecture diagram (SRS §4)

  • Components, modules and how they talk
  • Database, external systems, APIs
  • Each technology and why you chose it (Canvas: "very important")

4Scrum board on GitHub Projects

  • Sprints set up as milestones
  • Requirements split into stories & tasks, one card each
  • Every card has an owner and an estimate
  • Columns: To Do, In Progress, Done (template coming)
  • Labels: bug, enhancement, documentation
How it's marked: what a top grade needs
⚠ = graded by the rubric but missing from the Canvas task list
Process & communication
2.5 pts
Marked from: meeting minutes, project setup
  • Minutes for every meeting: attendance, agenda, discussion, decisions, action items, follow-up
  • A clear, complete Definition of Done
  • Every issue labelled Story, Task or Bug
  • Board shows the real, current status
Requirements & planning
2.5 pts
Marked from: user stories, backlog, sprint plan
  • Every story: "As a who, I want what, so that why"
  • Sprint 1 stories pass INVEST (Independent, Negotiable, Valuable, Estimable, Small, Testable)
  • Sprint 1 stories estimated and split into tasks
  • At least 15 more well-defined stories in the backlog
SRS & design
2.5 pts
Marked from: SRS document
  • Every SRS section complete and detailed
  • Every architecture decision justified: why, and what it affects
  • A wireframe for every screen
Testing
2.5 pts
Marked from: acceptance criteria
  • Every Sprint 1 story has acceptance criteria
  • Each one has a clear pass or fail
  • They describe the result, not how it's built
The takeaway: each of the 4 criteria grades something the task list never asks for. Skip those items and every criterion slides toward Pass or Fail.
Each criterion is out of 2.5. The grade bands:
